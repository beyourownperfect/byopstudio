================================================================================
  BYOPGateCS.studio — HOW TO CODE THIS PROJECT YOURSELF
  A practical, opinionated path to (re)building this app from zero.
================================================================================

If you want to write this codebase end-to-end as a solo developer, this file is
the no-fluff roadmap. It assumes you can already write basic JavaScript and
Python. The skills are listed in the order you will actually use them.


--------------------------------------------------------------------------------
 0. MINDSET BEFORE YOU TYPE A LINE
--------------------------------------------------------------------------------
- Ship the smallest thing that proves the loop. The "loop" here is:
    add a question -> solve it -> SRS schedules the next review -> Pulse shows it.
  Everything else (CSV import, momentum, mobile polish) is icing.

- Single-user means: no auth, no multi-tenancy, no migrations. Use this freedom
  to move fast. Don't add auth until you actually need it.

- Optimize for daily use, not benchmarks. A 200ms render that helps you stay
  consistent beats a 20ms render that breaks every week.

- Single-file backend on purpose. `server.py` holds everything. Don't split
  prematurely; you'll just move code around without learning anything.


--------------------------------------------------------------------------------
 1. THINGS YOU MUST KNOW BEFORE STARTING
--------------------------------------------------------------------------------
JavaScript / React
  - ES2020+ syntax (let/const, arrow fns, async/await, destructuring, optional chaining).
  - React function components and the four hooks you'll use 90% of the time:
      useState, useEffect, useMemo, useRef.
  - Controlled inputs and lifting state up.
  - React Router v6/v7: Routes, Route, NavLink, useNavigate, useSearchParams, Outlet.
  - How fetch / axios works and why you put the base URL in an env var.
  - Tailwind: utility classes, responsive prefixes (sm:, md:, lg:), arbitrary
    values ("hsl(var(--accent))"), and how to add a global CSS variable.

Python / FastAPI
  - async / await and why you must NOT do blocking I/O in an async route.
  - Pydantic v2: BaseModel, Field(default_factory=...), Literal, Optional.
  - FastAPI basics: APIRouter, path/query params, response_model, HTTPException.
  - dotenv: how python-dotenv loads .env at startup.

MongoDB / Motor
  - Documents, collections, _id (and why we keep our own `id: str` UUID instead).
  - Basic queries: find, find_one, insert_one, update_one ($set, $inc, $in),
    delete_one/many, count_documents, sort, projection ({"_id": 0}).
  - The async API (Motor) returns coroutines: you must await everything.

Tooling
  - Yarn (not npm) for the frontend.
  - pip and venv (or pipx) for the backend.
  - Supervisor or just two terminals for local dev.
  - A REST client (curl, HTTPie, or Postman) to test endpoints before the UI exists.

Domain knowledge (this is the secret weapon)
  - Read the GATE CS syllabus once. Knowing the 12 subjects you care about
    (C, DS, AL, OS, DB, COA, TOC, CD, DL, EM, DM, CN) keeps the UI honest.
  - Skim a Leitner-system or SM-2 explainer. Our SRS uses simplified Leitner.
  - Try Anki for two days. You'll feel exactly why the SRS matters.


--------------------------------------------------------------------------------
 2. THE PATH — DO IT IN THIS ORDER
--------------------------------------------------------------------------------

PHASE A — Skeleton (Day 1, ~3 hours)
  1. `mkdir byop && cd byop`
  2. Set up backend:
       python -m venv .venv && source .venv/bin/activate
       pip install fastapi uvicorn motor python-dotenv "pydantic>=2"
       create backend/server.py with one route: GET /api/ -> {"status":"ok"}
       run: uvicorn server:app --reload --port 8001
       curl http://localhost:8001/api/  -> verify.
  3. Set up frontend:
       npx create-react-app frontend  (or use CRA + craco like this project)
       add axios, react-router-dom, lucide-react
       put REACT_APP_BACKEND_URL in frontend/.env
       wire one fetch in App.js that calls /api/ and prints "ok".
  4. Tailwind: install per docs, set up index.css with a CSS-variable theme.
       This is where the project's monochrome+accent design comes from.
  5. Verify: yarn start opens 3000, calls 8001, sees "ok". Commit.

PHASE B — Question CRUD (Day 2)
  1. Define the Question Pydantic model on the backend.
  2. POST /api/questions, GET /api/questions, PUT/{id}, DELETE/{id}.
  3. On the frontend: a Repository page with a table, "New question" modal.
  4. Use a single `api.js` axios wrapper. Never hardcode URLs in components.
  5. Add data-testid on every interactive element from day one. Future-you
     will thank present-you when E2E tests come.

PHASE C — Practice + SRS (Day 3-4) — THE HEART OF THE APP
  1. Add Attempt and SrsRecord Pydantic models. Each question gets one srs doc.
  2. POST /api/practice/submit:
        - record the attempt
        - update srs: if correct -> interval_idx += 1 (cap at 5)
                      else -> interval_idx = 0
                      next_review_date = today + SRS_INTERVALS[idx]
        - return mastery + next-review date
  3. GET /api/practice/next?mode=due:
        - return any srs doc with next_review_date <= today
  4. Build the Practice page: question card, options, confidence slider,
     submit, feedback card.
  5. Render LaTeX with react-katex (`$...$` -> InlineMath, `$$...$$` -> BlockMath).
  6. Compute mastery in one helper and use it everywhere.

PHASE D — Pulse dashboard (Day 5)
  1. GET /api/pulse aggregates:
        - due_revisions (count srs with next_review_date <= today)
        - today's questions / minutes from study_logs
        - momentum (the 5-bucket formula in server.py)
        - weak topics (last 30 days, min 3 attempts, < 70% accuracy)
        - subject completion (% with mastery >= 60)
        - GATE readiness (PYQ %, revision readiness, mock readiness)
        - mission = top 4 prioritized actions
  2. Build the Pulse page with cards. Resist designing it until backend works.

PHASE E — Log + Timeline (Day 6-7)
  1. StudyLog + TimelineEntry models. Timeline entry auto-creates a study log.
  2. Stopwatch in the Log page: useState for elapsedMs, setInterval(250ms),
     persist running state with a ref so re-renders don't reset it.
  3. Timeline page: daily / weekly / monthly views. Use date math, no date lib.
  4. Schedule revisions: POST /api/timeline/{id}/schedule-revision with a date.
  5. Make sure scheduled revisions surface BOTH on Timeline (target date) AND
     in Pulse's `due_revisions` count. This is the most-broken bit if you skip it.

PHASE F — Polish (Day 8)
  1. Filters, sort, search, multi-select on Repository.
  2. CSV import/export with PapaParse.
  3. Cmd/Ctrl-K command palette (just a modal that focuses an input).
  4. Help (?) popups per page using a single reusable component.
  5. Mobile: hamburger drawer, bottom-sheet modals, overflow-x-auto on tables.
  6. Vercel deploy for the frontend; Render/Railway for the backend; Atlas for DB.


--------------------------------------------------------------------------------
 3. WHAT WILL TRIP YOU UP (READ THIS BEFORE YOU GET STUCK)
--------------------------------------------------------------------------------
- MongoDB ObjectId is NOT JSON-serializable. Always:
    (a) generate your own `id: str(uuid.uuid4())`, and
    (b) project with {"_id": 0} on every find().

- Motor returns COROUTINES. If you forget `await`, you'll set a field to
  `<coroutine object>` and waste an hour debugging.

- `datetime.utcnow()` is deprecated in 3.12+. Use `datetime.now(timezone.utc)`.

- CRA + Tailwind: import `index.css` once in `index.js`. Use `@layer` blocks for
  base/components/utilities so Tailwind's purge doesn't drop your custom classes.

- React Router v6/v7: nested routes need <Outlet/> in the parent (we use Layout).
  `useSearchParams` returns [params, setParams] — setParams takes an object.

- Hot reload death loops: don't call setState inside a useEffect that lists that
  state in deps. Use refs or split the effect.

- LaTeX errors crash the page if you forget to wrap user content in a try/catch.
  We render via a <Latex/> component that handles bad input.

- CORS: in production, set CORS_ORIGINS to the exact Vercel URL, no trailing slash.

- Vercel + Python backend: WON'T WORK as a serverless function (Motor connection
  pool dies between invocations). Host the backend separately. Use Vercel only
  for the React frontend.

--------------------------------------------------------------------------------
 5. HOW TO KEEP IT MAINTAINABLE AS IT GROWS
--------------------------------------------------------------------------------
- One file per page; no shared mega-component files. If a page grows past
  ~400 lines, extract the row/card subcomponent, not "utilities".

- Don't add a state manager (Redux, Zustand) until you have at least three
  pages that genuinely need shared state. Local useState + URL params + a tiny
  localStorage key (see Repository's filter persistence) goes very far.

- Resist building generic abstractions. The first time you write a
  "form library", you'll regret it. Copy-paste two forms first; abstract on
  the third only if the duplication is painful AND identical.

- Every interactive element gets a `data-testid`. It is the cheapest insurance
  you will ever buy.

- When the backend file passes ~1500 lines, that's the time to split it. Not
  before. Split by domain (questions.py, srs.py, pulse.py), not by layer.

React + Tailwind + FastAPI + Motor + MongoDB.
